PHASE 1: THE DATABASE ENGINE & ADVANCED SQL (ACADEMIC CRITERIA)
[ ] 1. The "Order History" Trigger [Checklist Item #4]

Write a PostgreSQL Trigger log_status_change on the orders table.
Action: Whenever an order's status changes (e.g., 'Pending' -> 'Preparing'), automatically insert a record into the order_status_history table.

[ ] 2. The "Loyalty Tier" Function [Checklist Item #5]

Write a PostgreSQL Function calculate_loyalty_tier(user_id).
Action: Sums the user's total spending from past orders and returns a computed string value (e.g., 'Bronze', 'Silver', 'Gold').

[ ] 3. The "Checkout" Procedure [Checklist Item #6]

Write a PostgreSQL Stored Procedure process_checkout(user_id, cart_items).
Action: A multi-step workflow that deducts the wallet balance, inserts into orders, inserts into order_items, and deducts inventory.

[ ] 4. Complex Analytics Queries [Checklist Item #7]

Query 1 (Top Pizzas): JOIN item, order_items, orders. Use GROUP BY and SUM to find highest selling items.
Query 2 (Delivery Speed): JOIN orders and order_status_history. Use AVG() to calculate the time between 'Pending' and 'Delivered'.
Query 3 (VIP Customers): JOIN users and orders. Use GROUP BY and SUM to rank top 10 highest-spending customers.


PHASE 1 EXTENSION: DATABASE OPTIMIZATIONS & INTEGRITY
[ ] 15. Add Database Indexes for Frequent Queries

Action: Create indexes on high-traffic columns like orders.created_at, orders.status, stock_log.ing_id, and customers.email. Use PostgreSQL's EXPLAIN ANALYZE to test.
Rationale: In real-world apps, unindexed queries slow down during peak hours (e.g., dinner rush). This prevents performance bottlenecks in analytics queries like delivery speed.

[ ] 16. Implement Data Validation Constraints

Action: Add CHECK constraints (e.g., item_price > 0, stock_log.change_amount != 0) and UNIQUE indexes (e.g., on coupons.code).
Rationale: Prevents invalid data entry (e.g., negative stock), which your triggers can enforce but constraints handle at the DB level for faster, fail-safe integrity.

[ ] 17. Set Up Automated Backups and Auditing

Action: Write a cron job or use pg_dump for daily backups; add a trigger to log all DML changes to an audit table (beyond order_status_history).
Rationale: Real businesses need data recovery (e.g., after accidental deletes) and compliance (e.g., tracking who changed inventory).



PHASE 2: BACKEND SECURITY & API (NODE.JS / EXPRESS)
[ ] 5. Custom Authentication System [Checklist Item #1]

Install bcryptjs and jsonwebtoken (or express-session).
Create POST /api/auth/register (Hash passwords before inserting into users).
Create POST /api/auth/login (Compare hash, return JWT or session_id).
STRICT RULE: Do not use Firebase or Auth0.

[ ] 6. Route Protection Middleware [Checklist Item #2]

Create verifyToken middleware to parse the JWT/session.
Create isAdmin and isReceptionist middleware to check the role column.
Apply this validation to EVERY page and HTTP request (except public menu browsing).

[ ] 7. Explicit Transaction Control [Checklist Item #3]

In your checkout API controller, implement explicit SQL transactions.
Must include BEGIN; at the start.
Must include COMMIT; upon success.
Must include ROLLBACK; in the catch (error) block if wallet funds are low or inventory is out of stock.

[ ] 8. Backend Validation (Never Trust the Frontend)

Cart Price Validation: Backend must query the item table to calculate the total order cost (do not trust the price sent by React).
Coupon Validation: Check the coupons table to ensure codes are valid/unexpired before applying discounts.


PHASE 2 EXTENSION: ADVANCED SECURITY & API ENHANCEMENTS
[ ] 18. Input Sanitization and Anti-XSS Measures

Action: Use libraries like validator.js in Node.js to sanitize all user inputs (e.g., customer names, addresses); enable helmet.js for security headers.
Rationale: Prevents injection attacks or XSS in forms (e.g., malicious script in order notes), which checklists overlook but are critical for PCI compliance in payments.

[ ] 19. Rate Limiting and API Throttling

Action: Install express-rate-limit; apply to login/register endpoints (e.g., 5 attempts/min) and public APIs like menu browsing.
Rationale: Protects against brute-force attacks or DDoS, especially for a public-facing app where bots could spam orders.

[ ] 20. Secure Payment Integration

Action: Integrate a real gateway like Stripe (sandbox mode) instead of mock payments; ensure no card data is stored in DB.
Rationale: Your payment table is basic—real-world e-commerce requires encrypted, compliant handling to avoid fraud liability.

[ ] 21. Error Handling and Logging Middleware

Action: Create global error middleware in Express; log errors to a file or service like Winston/Sentry, without exposing stack traces to users.
Rationale: Checklists focus on transactions (item #3), but real apps need traceable errors (e.g., why a checkout failed) for debugging without downtime.
